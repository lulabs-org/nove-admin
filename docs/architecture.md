# 项目架构设计原则

## 目录结构设计原则

本项目采用分层架构设计，遵循以下核心原则：

### 1. **shared** - 共享层

存放"可复用、无业务语义"的基础设施代码。

**职责：**

- 提供通用的工具函数和类型定义
- 封装第三方库（如 axios 封装、本地存储等）
- 提供可复用的 UI 组件
- 实现通用的 React Hooks

**原则：**

- 可复用，无业务语义
- 不依赖业务逻辑
- 可以被任何 feature 使用
- 保持独立性和可测试性

**示例：**

```
shared/
├── router/
│   ├── types.ts       # 路由类型定义
│   └── utils.tsx      # 路由工具函数
├── components/
│   ├── Layout.tsx     # 通用布局组件
│   └── Sidebar.tsx    # 通用侧边栏组件
├── hooks/             # 通用 React Hooks
├── utils/             # 纯函数工具
└── types/             # 通用类型定义
```

### 2. **features** - 功能层

按业务域拆分，每个 feature 代表一个独立的业务功能模块。

**职责：**

- 实现具体的业务功能
- 管理业务相关的状态和逻辑
- 提供业务特定的组件和服务

**原则：**

- 按业务域拆分，高内聚
- 可以使用 shared 中的代码
- 不依赖其他 features（避免循环依赖）
- 每个 feature 应该是独立的

**示例：**

```
features/
├── auth/              # 认证相关功能
│   ├── components/    # 认证专用组件
│   ├── hooks/         # 认证专用 hooks
│   ├── services/      # 认证 API 调用
│   ├── types/         # 认证类型定义
│   ├── routes.tsx     # 认证相关路由
│   └── index.tsx      # 入口文件
├── users/             # 用户管理功能
│   ├── routes.tsx     # 用户管理路由
│   └── ...
├── dashboard/         # 仪表盘功能
│   ├── routes.tsx     # 仪表盘路由
│   └── ...
└── settings/          # 系统设置功能
    ├── routes.tsx     # 系统设置路由
    └── ...
```

### 3. **app** - 应用层

只负责组装，将各个模块组合成完整的应用。

**职责：**

- 组装所有 features 的路由
- 配置应用级别的 Provider
- 配置应用级别的 Layout
- 应用初始化和启动

**原则：**

- 只负责组装，不包含业务逻辑
- 协调各个模块之间的协作
- 保持简洁，避免过度设计

**示例：**

```
app/
├── providers/
│   └── AppProviders.tsx    # 应用级别的 Provider 配置
├── routes.tsx              # 组装所有 features 的路由
└── layout.tsx              # 应用级别的 Layout 配置（如需要）
```

## 架构优势

1. **清晰的职责分离**：每个层级有明确的职责边界
2. **高内聚低耦合**：业务模块独立，依赖关系清晰
3. **易于维护**：代码按业务域组织，修改时影响范围小
4. **便于扩展**：新增功能只需在 features 中添加新模块
5. **团队协作友好**：不同开发者可以并行开发不同的 features

## 开发指南

### 添加新功能时

1. 在 `features/` 下创建对应的业务域目录
2. 按照标准目录结构组织代码（components、hooks、services、types、routes.tsx）
3. 在 `app/routes.tsx` 中导入并注册新路由
4. 如需新的共享工具，在 `shared/` 中添加

### 判断代码应该放在哪里

- **如果是通用的、可复用的、无业务语义的** → `shared/`
- **如果是特定业务功能的** → `features/对应业务域/`
- **如果是应用级别的组装配置** → `app/`

## 注意事项

- ❌ 避免在 `shared/` 中包含业务逻辑
- ❌ 避免在 `features/` 之间直接依赖（通过 shared 间接依赖）
- ❌ 避免在 `app/` 中包含业务逻辑
- ✅ 保持每个 feature 的独立性
- ✅ 保持 shared 的通用性
- ✅ 保持 app 的简洁性
